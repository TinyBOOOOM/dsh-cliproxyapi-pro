# Media engine and apply-level generation

## Classification and settings

- `lib/media/` and `lib/host/apply/`: `detectMediaKind()` classifies a parsed catalog model (catalog `type` / output modalities first, then the families CPA's own `openai_{images,videos}_handlers.go` route — compare against those when CPA adds one); `effectiveKind()` applies a user override. `parseCatalog()` stores `detectedKind`, `catalogType` and `outputModalities`; `discoverCpa()` merges the plain listing (`mergeListing()`: owner, type, modalities, plus media models only the listing carries). `CpaRuntime.withKinds()` computes kinds from `deps.mediaKindOverrides(accountId)` on every use, so an override applies without a new probe; `buildPiAiRoutes()`, `seedSelection()` and `recommendedModels` see chat models only (`isChatModel()`).
- Preferences: `loadMediaSettings()` / `saveMediaSettings()` / `applyMediaPatch()` (strict, `MediaError` codes) over `<profileDir>/.dsh-cliproxyapi/media-settings.json` `{ version: 1, agentTool, outputDir, defaultVideoSeconds, defaultVideoResolution, imageConfirm, videoConfirm, videoBudget, lastSelection, accounts: { [id]: { disabledModels, kindOverrides } } }`; every field has an effect (`agentTool`, `imageConfirm`, `videoConfirm` and `videoBudget` drive the agent tool).
## Model choice and image admission

- Model choice: `mediaOptions()` (enabled models of enabled accounts, ref `accountId/modelId`), `matchMediaModel()` (ref → exact id → unique fragment; ambiguity is an error, never a guess) and `chooseMediaModel()` (request → session pick → last pick → only option). `createMediaSessionStore()` owns `media-sessions.json` (per-session `image`/`video` picks, the newest 48 `runs` — display records normalized by `normalizeRun()`: status `running`/`done`/`error`, model, prompt, options, times, folder label, error code/summary, never paths — and the newest 48 output paths with their `commandId`, 500 sessions; `media/session` lists 12). `/cpa-image` (`runImageCommand` in `apply`) admits synchronously: `parseImageCommand()` → `chooseMediaModel()` → working directory → attachment bytes via `attachments.readImage()` → `controller.mediaEndpoint()` (the model's own account only) → records a `running` run and returns success at once (the composer keeps the draft until the handler returns, so a long handler left the command in the input). `startImageJob()` then runs `generateImages()` (`b64_json`;
  - URL results only `data:`/HTTPS, bounded, without the key; 3-minute timeout;
  - URL-free error summaries) → `writeOutputFiles()` (`wx`, never replaces a file) under `outputDirectory(cwd, outputDir)` in the background (own `AbortController`, aborted on dispose → `interrupted`) and records `done`/`error` through `recordRun()`.
## Session running status and file results

- DSH counts only agent turns as running and has no plugin API for it, so while a job runs the plugin emits the host event `api-session/status` (`sessionId`, `true`) — at start, every 5 s (`MEDIA_HEARTBEAT_MS`; list refreshes reset it) and after `agent/status` goes idle — and `false` when the session's last job settles unless the agent itself is running.
- The composer then shows a Stop button that cannot stop the job; messages are sent normally. `media/command` returns `{ run, files, folderPath, desktop }` (`desktop` = `explorer` / `finder` / `filemanager` from `process.platform`) (each file with its absolute `path`, so the page can open / reveal it through DSH's Session Remote, which re-verifies the path on the Host); a stored `running` run without a job in this activation reads as `interrupted`.
## Video admission, polling and recovery

- Both parsers also take plain-language options as whole words at the start or end of the prompt (`takeNaturalOptions()`: `10秒` / `10s`, `480p`, `16:9`, `竖屏` / `portrait`, `横屏`, `方形`, `2张`; explicit flags win; out-of-range values are errors, not prompt text). `/cpa-video` (`runVideoCommand`) admits the same way (`parseVideoCommand()`; `videoMode()` maps the image count and `--ref` / `--first-last` / `--last` (or the words 参考图 / 首尾帧 / 尾帧) to `text` / `first-frame` / `reference` (2+ images by default; 14 on 1.5, else 7) / `first-last` / `last-frame` (pinned frames need `grok-imagine-video-1.5`), sent as `image` / `last_frame` / `reference_images`; `-s` / `-r` default to `defaultVideoSeconds` / `defaultVideoResolution`), records a `running` video run and returns; `startVideoJob()` calls `submitVideo()` (native `POST /v1/videos/generations`: `model` via `videoRequestModel()` — `sora-2*` → `grok-imagine-video`, because the native route accepts only Grok ids — `prompt`, `duration`, `resolution`, optional `aspect_ratio` / `image.url`), stores the job in `media-jobs.json` (`createMediaJobStore()`, `normalizeJob()`: request id, account, model, session, command id, cwd, outputDir, prompt, seconds, times, state `submitted`/`done`/`failed`/`expired`; never keys or URLs; finished jobs kept 7 days) and `followVideoJob()` polls `retrieveVideo()` (native `GET /v1/videos/{id}`; `videoState()` maps xAI/OpenAI words; 5 s → 10 s after 1 min → 15 s after 3 min; transient failures retried up to 12 times) until done, then `downloadVideo()` streams `GET /openai/v1/videos/{id}/content` (CPA fetches xAI's URL with the credential's proxy; the plugin never contacts the upstream host or follows `video.url`) into a `wx` file (MP4/MOV/WebM by magic bytes, `MAX_VIDEO_BYTES` 200 MiB, partial files removed).
- A dispose abort only pauses a submitted job (nothing is recorded); `resumeVideoJobs()` in the next activation picks up every `submitted` job, and one older than `VIDEO_JOB_TTL_MS` (CPA's 3-hour request → credential binding) becomes `expired` without a request.
- Cut off before CPA returned a request id = `interrupted`. `videoLive` (in memory) adds `phase` (`submitting`/`queued`/`running`/`downloading`) and `progress` to `media/command`. `/cpa-video-status` lists the session's jobs as text. `/cpa-video-edit` / `/cpa-video-extend` (`runVideoEditCommand(mode)`, `parseVideoEditCommand()`: `--from <command id>`, extend `-s 2-10`) reuse a finished video's own short-lived xAI result URL, which `retrieveVideo()` returns as `sourceUrl` (HTTPS only) and `rememberSource()` keeps **in memory only** (`videoSources`, 100 entries, `VIDEO_SOURCE_TTL_MS` 1 h; never stored, logged or returned to the page — `media/command` only reports `actions: { edit, extend, expiresAt }`); `submitVideoEdit()` posts `{ model: grok-imagine-video, prompt, video: { url }, duration? }` to `/v1/videos/edits` or `/extensions` (xAI: edit source ≤ 8.7 s, extend source 2–15 s, +2–10 s).
## Video edit / extend sources and limits

- The commands accept any MP4 (design D9 override): one source from an attached file block (`{ type: "file", attachment: { attachmentId, name, bytes } }`, read via `attachments.fileHostPath()` or `readFileStream()`), `--video <path>` (relative to the session cwd), `--url <http(s)>` (no credentials; xAI downloads it; only the host is recorded as `sourceName`), `--from <command id>`, or a video path typed at the start or end of the prompt (`VIDEO_PATH_HEAD` / `VIDEO_PATH_TAIL`: quoted, `@`-prefixed, absolute with spaces up to the first `.mp4|.m4v|.mov`, or one word; an explicit source wins), or by default the session's newest video file — a plugin-made video uses its remembered link while usable, otherwise its recorded file (`sessionVideoFile()`);
- Natural words the routes cannot use (resolution, ratio; an edit's length — `takeNaturalOptions()` kinds `edit` / `extend`) are removed from the prompt and stored as the run's `ignored` (shown as a tag). `-m` picks the account for non-plugin sources (else the source's own account, else `chooseMediaModel()`).
- Local bytes go inline as `data:video/mp4;base64,…` (`sourceData`), at most `VIDEO_UPLOAD_MAX_BYTES` 14 MiB (the edit route read a 20 MiB body, measured; `VIDEO_UPLOAD_BODY_MAX_BYTES`) with a 5-minute request timeout; `isMp4()` / `mp4Duration()` (top-level `moov/mvhd`) refuse non-MP4s and out-of-range lengths before any request.
- An upstream 405 becomes `route-unsupported`; `unsupportedRoutes` (in memory, `accountId/route`) then refuses that route up front and hides the row's action (CPA cools a credential down ~1 min after a 405). `media/command` reports `actions` while a link is remembered or the video file exists within the upload cap (`expiresAt` only with a link).
## Chat-model parameter interpretation

- Every generation command then asks the session's chat model for parameters the rules missed (`interpretParams()` in `apply`, inside the background job before the upstream request, phase `interpreting` in `videoLive`): target = `agent.session.requestHeader().config`, else `agent.options`, else `agentDefaultModel`; `ctx.llm.stream({ provider, model, system, messages, maxTokens: 2000, sessionId, purpose: "cpa-media-params" })` with a 30 s timeout; question / validation in `lib/media/` (`interpretationRequest()`, `parseInterpretation()`, `interpretedPrompt()` — the prompt may only lose characters, a subsequence keeping ≥ 30 % unless ≤ 12 characters were removed — and `interpretationLabels()`).
- Fields the rule parser already set are never asked for or overridden; only the prompt text and the image count are sent.
- Failures never block the run (`interpreted.failed`); the run records `interpreted: { by, items, failed?, prompt? }` and the updated mode / prompt / length; `startVideoJob()` takes the final `prompt` / `seconds` returned by `submit`.
## Agent tool lifecycle and session policy

- The agent tool (`executeGenerateMedia()` in `apply`; pure parts in `lib/media/`: `GENERATE_MEDIA_TOOL` / `GENERATE_MEDIA_OUTPUT`, `parseToolArgs()`, `toolCommandLine()`, `toolRunId()`, `approvalText()`, `agentPolicy()`, `chargeSeconds()`, `applySessionPolicy()`) runs the same handlers as the slash commands with a command line built from its arguments and extra invocation fields: `literal` (no plain-language parsing, no interpretation), `pickSession` (the root session's model pick; the root is found through `agents.list()` / `isOwnedBy()`), `commandId` = `toolRunId(exec.callId)` (the run is recorded in the calling agent's own session) and `gate(plan)`, called after admission and before anything is recorded or sent, which enforces the budget / generation-cost consent and charges seconds (a `gateError` passes through the handler's catch).
- It does not append synthetic `command/run` / `command/done` records: the client derives the standalone media row from the existing durable tool lifecycle.
- The output and presentation meta retain deprecated `commandRow: false` for compatibility; this flag no longer selects the rendering surface or suppresses cards.
- No new Session event type is introduced.
- Local `images` are saved through `attachments.saveImage()` and passed as attachment blocks.
- The tool then waits on `jobPromises` (filled by `settleWith()` in `startImageJob()` / `trackVideoJob()`) for up to 10 minutes; a timeout or abort returns `status: "running"` while the job continues.
- Image results carry `previews` (attachment refs rendered as image blocks) when `llm.resolveModelInfo()` of the calling route declares image input.
- Session overrides live in `media-sessions.json` (`imageConfirm`, `videoConfirm`, `videoBudget`, `usedSeconds`, `budgetKey`, `lastConfirm`); `media/session` reports `agent: { enabled, imageConfirm, videoConfirm, videoBudget, used, sources, global }` and the exact session's compatibility-only `pendingConfirmations` (never native questions); `media/session/save` accepts the overrides (`inherit` clears).
## Reference size budgets, serving and diagnostics

- Attached references go through `readReference()` in `apply`: kept when within budget (video images share `videoImageBudget(prompt, count)`, derived from the measured `VIDEO_GENERATION_BODY_MAX_BYTES` 1 MiB — `/v1/videos/generations` read 1 MiB and refused 1.2 MiB — capped at `FIRST_FRAME_MAX_BYTES`; image-edit references `REFERENCES_MAX_BYTES` 1.4 MB split evenly, unmeasured), a PNG is re-encoded by `fitReferenceImage()` (`decodePng()` via node:zlib, `fitRgb()` flatten on white + area downscale to `REFERENCE_MAX_EDGE` 1280, baseline `encodeJpeg()`, quality / size ladder), any other format asks `attachments.readImageRequest(ref, { width, height, maxBytes })`, else `reference-too-large` at admission — `postVideoJob()` refuses a body over its route's limit locally (`request-too-large`) and maps the upstream's "Failed to read request body: length limit exceeded" (400/413) to the same code. `media/file` serves only paths recorded for that session (videos streamed with single-range `Range` support via `byteRange()`, 206/416); `media/session` returns file names and ids, never paths, syncs once (`mediaChoicesFor`) when no generation model is offered yet because a catalog is unread (or when a needed kind is missing and an enabled account's last catalog read missed the plain listing, at most once per 30 s), and reports `catalogIncomplete` while that read is outstanding. `diagnoseMedia()` sends GET requests only: both catalogs with the key (fixed descriptive fields of media-looking entries, never other values), and two video route probes **without** the key (401 = present, CPA's plain-text 404 = missing).

## Generation and consent invariants

- **At most one agent tool, `generate_media`, off by default.** It is registered only while `media-settings.json` `agentTool` is on and an enabled account offers an enabled generation model (`syncAgentTool()` after every POST route, refresh and `/cpa-refresh`); otherwise no tool exists and no context is used.
  - Its definition is static (`GENERATE_MEDIA_TOOL`, compact, no model or account lists).
  - Optional arguments accept `null` so Responses strict schemas can express defaults; `parseToolArgs()` also accepts legacy empty optional strings, video `count: 1` and `first-frame` with no images as neutral defaults, without guessing a model, batching videos or inventing an image.
  - The tool description and the `prompt` parameter require the user's prompt verbatim and forbid expanding it into a longer scene description or adding unrequested camera / lighting / style / character / environment details.
  - Account management, quota and updates are never exposed as tools (the former `cliproxyapi` tool cost ~3K tokens in every session). `apply()` injects `tools` only for this (asserted in the Host tests under `tests/host/`).
- Image / video models (effective kind ≠ chat) never enter `llm-pi-ai` routes, recommendations or seeded selections; a saved `selectedModels` naming one is kept as is.
  - Media preferences never go into `state.json` or `GLOBAL_FIELDS`; a damaged `media-settings.json` loads as defaults and is kept as `*.corrupt-*.json` on the next save.
  - The diagnostic stays read-only (GET only, no generation, no upstream-spending probe) and never returns the key.
  - Generation runs only on an explicit user action (`/cpa-image`, `/cpa-video`, `/cpa-video-edit`, `/cpa-video-extend`, the row buttons that run them, or a `generate_media` call while the user has switched the tool on), calls only the chosen model's account, never retries on another account, never overwrites a file, and never puts keys, upstream URLs or response bodies into results, logs or session files. xAI's result URL may live only in memory for edit / extend and never in files, logs or page data.
  - A submitted video cannot be cancelled: never claim otherwise, never resubmit a job automatically, and download only through CPA's content route.
  - Video jobs keep no keys or URLs, resume after a reload only within `VIDEO_JOB_TTL_MS`, and a dispose never records a paused job as failed.
  - Manual `/cpa-video` (and every slash command or row button) neither asks for approval nor counts against a budget (design D6).
  - The agent tool asks whenever the effective confirmation is `ask`, independently of DSH execution-approval permissions: `askNativeConfirm()` calls `ctx.userQuestions.ask({ agent: rootAgentOf(exec.agent), signal, questions })` with no `wait` or `callId`, so the live root session's native composer owns the pending question instead of a continued tool card.
  - The question and options are bilingual (`Allow / 允许`, `Decline / 拒绝`); only the single exact Allow selection for the expected question id, without custom text, grants consent.
  - It never calls `approval.request` or interprets the full-access preset as cost consent.
  - A 10-minute deadline, tool abort/disable or plugin dispose cancels the question and refuses consent; malformed answers, unavailable answerers and native errors fail closed and never switch to fallback.
  - Only when `userQuestions` is absent does `pendingConfirms` own an in-memory compatibility request for the live human root session, including calls made by its subagents (not the child session): `sessionView().pendingConfirmations` exposes `{ commandId, kind, en, zh, expiresAt }` only for that session, and `MediaConfirmationDock` answers through `POST media/confirm` from the same session.
  - No chat row owns consent controls.
  - It never treats a non-grant as allowed, counts every agent video's seconds on the root session (also when confirmed), refuses over the limit only in `auto`, refunds only when the run ended without a request id and with a not-submitted error code, and restarts the count when the limit changes or confirmation turns from `ask` to `auto`.
  - The only host event the plugin emits is `api-session/status` for a session with a running generation job, and it always settles it back to idle (unless the agent runs) when the jobs end or the plugin is disposed.
